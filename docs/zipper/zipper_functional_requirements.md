# Функциональные требования к Zipper

## 1. Назначение

Zipper — это голосовой локальный агент внутри текущего приложения Dictator.

Пользователь обращается к Zipper голосом и просит выполнить небольшое действие
на компьютере: открыть информацию, обработать содержимое буфера обмена, открыть
URL, выполнить разрешённую команду или вызвать подключённый инструмент.

Zipper является продолжением текущего приложения, а не отдельным
самостоятельным модулем со своим окружением, отдельным запуском и отдельной
инфраструктурой.

## 2. Запуск Zipper

У Zipper должен быть отдельный хоткей.

Хоткей Zipper должен настраиваться так же, как остальные хоткеи приложения.

Нажатие хоткея запускает запись голосовой команды для Zipper.

Повторное нажатие завершает запись и передаёт распознанный текст агенту.

Отмена команды должна быть возможна стандартным для приложения способом.

## 3. Голосовая команда

Zipper использует текущую механику голосового ввода приложения.

После записи голосовая команда распознаётся и передаётся агенту как
пользовательский запрос.

Команды Zipper не должны автоматически вставляться в активное поле ввода как
обычная диктовка.

## 4. LLM

Zipper использует текущую локальную LLM приложения через MLX Runtime.

Zipper, обычный LLM-пайплайн и reader-предобработка используют один LLM gateway
поверх общего runtime-cache. При запуске приложения LLM/VLM не загружается в
память; если пользователь не менял модель после запуска, первая команда
Zipper, reader-предобработка или LLM-запрос загружает текущую модель при
реальном использовании. При смене LLM/VLM старая модель освобождается, новая
выбранная модель прогревается в фоне. Загруженная LLM/VLM остаётся в памяти
между голосовыми командами, reader-сценариями и LLM-запросами до смены модели
или завершения приложения.

Не нужно добавлять отдельное подключение к внешнему LLM API.

Zipper должен использовать текущие настройки LLM приложения, если пользователь
не задал другое поведение в конфиге Zipper.

## 5. Агент

Zipper должен быть реализован как локальный агентский runtime поверх текущей MLX LLM.

Агент должен уметь выбирать нужные инструменты, выполнять их и возвращать
результат пользователю.

Агент должен работать в рамках текущего приложения и использовать уже
существующие возможности приложения там, где они есть: голосовой ввод,
голосовой вывод, popup/overlay, буфер обмена, LLM, хоткеи и настройки.

## 6. Вывод результата

У Zipper должно быть два способа вывода результата:

1. Голосовой ответ.
2. Всплывающее окно с текстом.

Агент сам выбирает, как ответить.

Короткие подтверждения можно озвучивать голосом через текущий TTS-профиль
приложения.

Голос и `Интонация TTS` для голосового ответа берутся из настроек Reader/TTS.
Агент выбирает способ вывода: голос, окно или оба варианта.

Голосовой вывод Zipper проходит отдельную TTS-подготовку: числа переводятся в
слова, markdown, URL, кодовые фрагменты, JSON и технические идентификаторы
убираются, а простая пунктуация `. , ? ! : ;` сохраняется как подсказка для
пауз. Инструмент озвучивания должен получать только готовую произносимую фразу:
обычные слова буквами, числа словами и без цифр.

Длинные ответы, списки, ошибки, результаты команд, URL, текст из буфера и
техническую информацию лучше показывать в окне.

Агент может использовать оба способа одновременно: коротко сказать голосом и
показать подробности текстом.

## 7. Встроенные инструменты

У Zipper должны быть встроенные инструменты:

```text
Получить текст из буфера обмена
Положить текст в буфер обмена
Получить текущие дату и время
Открыть URL в браузере
Показать текстовое окно
Озвучить текст
```

Инструменты работы с буфером обмена должны использовать обычный системный
буфер обмена.

Инструмент открытия URL должен открывать ссылку в браузере по умолчанию.

## 8. CLI-команды

Zipper должен уметь выполнять только те CLI-команды, которые явно описаны в
конфиге.

На первом этапе достаточно поддержать несколько заранее заданных команд.

Пользователь должен иметь возможность описать в конфиге:

```text
название команды
описание команды
что именно выполнять
нужно ли подтверждение перед выполнением
```

Агент не должен получать возможность выполнять произвольные команды, если они
не описаны в конфиге.

## 9. MCP

Zipper должен поддерживать подключение MCP из конфига.

На первом этапе достаточно 1–2 MCP.

Пользователь должен иметь возможность включить MCP-сервер в конфиге и дать
Zipper доступ к его инструментам.

Если MCP недоступен или не запустился, Zipper должен показать ошибку, но
приложение в целом должно продолжить работать.

## 10. Пользовательские инструменты

Должна быть возможность удобно добавить свои инструменты для Zipper.

Пользователь или разработчик должен иметь простой способ подключить свой
инструмент в конфиге и сделать его доступным агенту.

Подробности реализации не фиксируются в функциональных требованиях. Важно,
чтобы добавление своего инструмента не требовало переписывать основную логику
Zipper.

## 11. Конфигурация

Zipper должен настраиваться через файл конфигурации.

Конфигурация является частью текущего приложения, а не отдельным
самостоятельным механизмом.

Должны быть предусмотрены три варианта конфига:

```text
1. Пример конфига в репозитории.
2. Локальный конфиг в репозитории для запуска через uv.
3. Пользовательский конфиг установленного приложения.
```

Пример конфига должен быть закоммичен в репозиторий.

Локальный конфиг для разработки должен позволять запускать Zipper через обычный
запуск приложения из исходников:

```bash
uv run python main.py
```

Пользовательский конфиг установленного приложения должен храниться там, где
текущему приложению естественно хранить пользовательские настройки и файлы.
Конкретный путь должен быть выбран при реализации после проверки текущего
механизма хранения настроек приложения.

В конфиге должны настраиваться:

```text
system message агента
MCP
разрешённые CLI-команды
пользовательские инструменты
лимиты контекста
память агента
поведение debug-панели
```

Не нужно добавлять отдельные environment variables, отдельные режимы запуска или
отдельный внешний механизм конфигурации.

## 12. Контекст и память

Контекст Zipper должен сохраняться между запусками приложения.

У Zipper должна быть постоянная память в виде текстового блока.

Этот блок добавляется к system message агента.

Размер текущего контекста должен ограничиваться двумя параметрами:

```text
максимальное количество токенов
максимальное количество сообщений и вызовов инструментов
```

Значения по умолчанию:

```text
32768 токенов
200 сообщений и вызовов инструментов
```

Когда лимит превышен, старые сообщения и вызовы инструментов должны
суммаризоваться в постоянную память.

В постоянную память должны попадать:

```text
важные факты
устойчивые предпочтения пользователя
повторяющиеся действия
часто используемые команды
полезные выводы из предыдущих обращений
```

Если информация уже есть в system message или в постоянной памяти, она не должна
бесконечно дублироваться при новых суммаризациях.

## 13. Debug-панель

У Zipper должна быть debug-панель.

Она включается и выключается из меню приложения.

Когда debug-панель включена, справа появляется узкое окно на всю высоту экрана.

В debug-панели должны отображаться все события работы Zipper:

```text
что пользователь сказал
какой текст ушёл агенту
что ответила модель
какие инструменты агент вызвал
с какими аргументами
что вернули инструменты
какой финальный ответ был сформирован
какой вывод был выбран: голос, окно или оба
ошибки
события работы памяти
```

Debug-панель нужна для отладки поведения агента.

Не нужно делать сложную конфигурацию debug-панели.

Не нужно отдельно описывать скрытие секретов.

Достаточно требования: при включённой debug-панели разработчик видит полный
поток работы агента.

## 14. Меню

В меню приложения должен появиться раздел Zipper.

В нём должны быть доступны:

```text
включить / выключить Zipper
текущий статус Zipper
текущий хоткей Zipper
открыть конфиг Zipper
перезагрузить конфиг Zipper
включить / выключить debug-панель
очистить контекст Zipper
очистить постоянную память Zipper
```

Формулировки пунктов меню должны быть на русском языке, как и остальной
интерфейс приложения.

## 15. Ошибки

Если Zipper не смог распознать команду, он должен показать понятную ошибку.

Если LLM не ответила, он должен показать понятную ошибку.

Если инструмент завершился ошибкой, Zipper должен показать результат ошибки
пользователю.

Если конфиг некорректный, Zipper должен показать ошибку и не ломать остальное
приложение.

Если MCP недоступен, Zipper должен показать ошибку и продолжить работать без
этого MCP.

Ошибки Zipper не должны ломать обычную диктовку, Reader, TTS и остальные функции
Dictator.

## 17. Что входит в первый этап

В первый этап входит:

```text
отдельный хоткей Zipper
голосовое обращение к агенту
локальный агентский runtime
использование текущей LLM через MLX Runtime
конфиг Zipper
локальный конфиг для запуска через uv
пользовательский конфиг установленного приложения
постоянный контекст между запусками
суммаризация старого контекста в память
встроенные инструменты
подключение 1–2 MCP
разрешённые CLI-команды
пользовательские инструменты
голосовой ответ
текстовое окно
debug-панель справа
пункты меню Zipper
документация
тесты
```

## 18. Что не входит в первый этап

В первый этап не входит:

```text
wake word
постоянное прослушивание микрофона
отдельное приложение Zipper
отдельный LLM API endpoint
сложный редактор конфигурации
произвольное выполнение любых shell-команд
полноценный чат-интерфейс
отдельная система логирования поверх существующей
сложная настройка debug-панели
```

## 19. Критерии готовности

Функция готова, если:

```text
Zipper запускается отдельным хоткеем.

Пользователь может сказать голосовую команду.

Команда распознаётся и передаётся агенту.

Агент использует текущую локальную LLM через MLX Runtime.

Агент может прочитать буфер обмена.

Агент может записать текст в буфер обмена.

Агент может открыть URL.

Агент может вернуть текущую дату и время.

Агент может показать текстовое окно.

Агент может озвучить ответ.

Агент может выполнить разрешённую CLI-команду.

Агент видит инструменты подключённого MCP.

Контекст Zipper сохраняется между запусками.

После превышения лимитов старый контекст суммаризуется в постоянную память.

В меню есть раздел Zipper.

Debug-панель включается из меню и показывает поток событий агента.

Есть локальный конфиг для запуска через uv, не предназначенный для коммита.

У установленного приложения есть пользовательский конфиг Zipper.

Ошибки Zipper не ломают остальные функции Dictator.

README и AGENTS.md обновлены.

Тесты добавлены или обновлены.
```
